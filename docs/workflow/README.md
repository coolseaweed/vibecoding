# 바이브코딩 세션 워크플로우

바이브코딩은 AI에게 한 번에 “앱을 만들어줘”라고 요청하는 일이 아닙니다. 환경을 안정시키고, 문제를 구체화하고, 검증 가능한 목표를 세운 뒤, 결과를 직접 검수하는 반복 과정입니다.

한 세션은 **환경셋업 → 아이디에이션 → 플래닝(Goal) → 검수**의 네 단계로 진행합니다. 검수에서 문제가 발견되면 필요한 이전 단계로 돌아가 작은 루프를 반복합니다.

## 원샷 요청 템플릿

이 템플릿은 로컬 저장소 파일을 읽고 수정하며 터미널과 브라우저를 사용할 수 있는 **Codex CLI 또는 Claude Code**에 전달합니다. ChatGPT와 Claude Desktop의 일반 대화만으로는 로컬 코드 수정과 검증을 보장할 수 없습니다.

아래 템플릿의 대괄호 부분만 자신의 내용으로 바꿔 한 번에 전달합니다.

```text
저장소: [내 GitHub 저장소 URL]

먼저 AGENTS.md, llms.txt, README.md, docs/workflow/README.md를 읽어.
대상 사용자는 [누구]이고, 해결할 문제는 [문제]야.
이번 Goal은 [사용자에게 생길 결과]야.

범위: [이번에 만들 기능 또는 화면]
비범위: [이번에 하지 않을 일]
제약: [기술, 보안, 디자인 조건]
완료 기준:
- [사용자가 확인할 수 있는 결과 1]
- [사용자가 확인할 수 있는 결과 2]
- lint, typecheck, production build 통과
- 데스크톱과 모바일 브라우저 검수

환경셋업 → 아이디에이션 확인 → Goal 플래닝 → 최소 구현 → 검수 순서로 진행해.
Goal 기능을 지원하면 위 목표로 Goal을 생성해.
각 작업 단계에 검증을 붙이고, 권한·비밀값·비용·데이터 삭제가 필요하면 실행 전에 중단해.
완료 후 변경 내용, 검증 증거, 남은 제한을 보고해.
배포가 명시적으로 요청되고 승인된 경우에만 배포 URL도 보고해.
```

대상 사용자, 문제, 범위, 완료 기준이 비어 있으면 정확한 원샷 결과를 만들 수 없습니다. 모르는 항목은 AI가 임의로 정하게 두지 말고 먼저 작성합니다.

## 1. 환경셋업

### 학습 목표

코드를 만들기 전에 실행 환경, 계정, 권한, 저장소 상태를 확인합니다. 환경 문제가 코드 문제로 위장하는 시간을 줄이는 단계입니다.

### 확인할 입력

- 사용할 운영체제와 터미널
- GitHub 계정과 대상 저장소
- 패키지 매니저와 런타임 버전
- 기능에서 사용할 경우에만 Vercel·Supabase 개발 프로젝트
- Codex·Claude Code·ChatGPT·Claude Desktop 중 사용할 도구
- MCP의 읽기·쓰기 권한 범위

### 진행 방법

1. [환경 설정 체크리스트](../checklist/README.md)를 위에서부터 확인합니다.
2. 저장소를 clone하고 의존성을 설치합니다.
3. 기존 프로젝트라면 변경 파일과 실행 중인 서비스를 먼저 확인합니다.
4. 로컬 실행, lint, production build의 기준 상태를 기록합니다.
5. 비밀값은 소스가 아닌 승인된 저장 위치에 둡니다.

### 시작 프롬프트

```text
이 저장소에서 작업을 시작하기 전에 환경을 점검해줘.
Git 상태, 사용 중인 패키지 매니저, 실행·lint·build 명령,
필요한 외부 서비스와 MCP 범위를 읽기 전용으로 확인하고
빠진 준비 사항만 체크리스트로 알려줘. 아직 코드는 수정하지 마.
```

### 완료 기준

- 로컬 앱이 실행되고 기준 검증이 통과한다.
- 현재 Git 브랜치와 기존 변경을 알고 있다.
- 사용할 외부 서비스와 권한 범위를 설명할 수 있다.
- 비밀값이 저장소에 들어가지 않는다.

## 2. 아이디에이션

### 학습 목표

만들고 싶은 기능이 아니라 해결할 사용자의 문제를 먼저 정의합니다. 가능한 방향을 넓게 탐색한 뒤, 이번 세션에서 다룰 가장 작은 가치 단위를 선택합니다.

### 확인할 입력

- 누구의 어떤 문제인지
- 지금 사용자는 문제를 어떻게 해결하는지
- 해결됐다고 판단할 관찰 가능한 변화
- 반드시 필요한 것과 나중에 해도 되는 것
- 시간, 기술, 데이터, 권한 제약

### 진행 방법

1. 사용자와 상황을 한 문장으로 적습니다.
2. 서로 다른 해결 방향을 최소 세 가지 비교합니다.
3. 가장 단순한 방향을 선택하고 선택 이유를 적습니다.
4. 이번 세션에서 하지 않을 일을 명시합니다.
5. 핵심 사용자 흐름을 시작→행동→결과로 표현합니다.

### 아이디에이션 프롬프트

```text
대상 사용자는 [사용자]이고, [상황]에서 [문제]를 겪고 있어.
이 문제를 해결하는 서로 다른 접근 3가지를 제안해줘.
각 접근의 사용자 가치, 구현 난이도, 주요 위험을 비교하고
한 세션에 만들 수 있는 가장 작은 방향을 추천해줘.
아직 구현하거나 기능을 추가로 상상하지 마.
```

### 완료 기준

- 문제와 대상 사용자가 한 문장으로 정의된다.
- 선택한 방향과 버린 방향의 이유가 남아 있다.
- 핵심 흐름과 비범위가 명확하다.
- 결과를 확인할 방법이 있다.

## 3. 플래닝 (Goal)

### 학습 목표

아이디어를 AI와 사람이 같은 의미로 이해할 수 있는 검증 가능한 목표로 바꿉니다. Goal은 “무엇을 만들지”뿐 아니라 “어떻게 완료를 증명할지”를 포함합니다.

### 좋은 Goal의 구조

```text
목표: [사용자에게 생길 결과]
범위: [이번에 바꿀 화면·기능·파일]
비범위: [이번에 하지 않을 일]
제약: [기술·보안·디자인·호환 조건]
완료 기준: [테스트·빌드·사용자 흐름으로 검증할 조건]
```

### 진행 방법

1. 결과를 사용자 관점의 한 문장으로 씁니다.
2. 완료 여부가 참/거짓으로 판정되도록 성공 기준을 만듭니다.
3. 위험도가 높은 가정을 먼저 확인합니다.
4. 작업을 작은 순서로 나누고 각 단계에 검증 방법을 붙입니다.
5. 계획을 읽고 불필요한 기능과 추상화를 제거합니다.

### 플래닝 프롬프트

```text
선택한 방향을 구현 계획으로 바꿔줘.
먼저 한 문장의 Goal, 범위, 비범위, 제약, 완료 기준을 작성해.
그다음 각 단계마다 “작업 → 검증”이 짝을 이루는 짧은 계획을 제시해.
새 환경변수, 외부 서비스 변경, 데이터 삭제가 필요하면 실행하지 말고 표시해.
가장 단순하게 목표를 달성하는 경로를 선택해.
```

### 완료 기준

- Goal과 완료 기준이 구체적이다.
- 모든 작업 단계에 검증 방법이 있다.
- 범위 밖의 요청이 분리돼 있다.
- 권한, 비용, 데이터 손실 위험이 사전에 드러난다.

## 4. 검수

### 학습 목표

AI의 “완료했습니다”를 그대로 믿지 않고 코드, 동작, 보안, 사용자 경험을 증거로 확인합니다. 검수 결과는 통과, 수정 필요, 보류 중 하나로 명확히 남깁니다.

### 검수 순서

1. `git diff`로 요청과 관련된 변경만 있는지 확인합니다.
2. lint, 타입 검사, 테스트, production build를 실행합니다.
3. 핵심 사용자 흐름을 데스크톱과 작은 화면에서 직접 실행합니다.
4. 로딩, 빈 상태, 오류 상태, 키보드 사용을 확인합니다.
5. 비밀값, 과도한 권한, 위험한 데이터 변경이 없는지 확인합니다.
6. 완료 기준별 증거와 남은 제한을 기록합니다.

### 검수 프롬프트

```text
현재 변경을 구현자가 아닌 검수자 관점에서 확인해줘.
Goal의 완료 기준별로 코드 근거와 실행 검증 결과를 제시하고,
기능 오류, 회귀, 보안, 접근성, 과도한 범위 변경을 찾아줘.
문제가 있으면 심각도와 재현 방법을 적고 임의로 숨기지 마.
마지막에 통과 / 수정 필요 / 보류 중 하나로 판정해.
```

### 완료 기준

- 자동 검증과 핵심 수동 흐름이 모두 확인된다.
- 변경된 모든 줄이 Goal과 연결된다.
- 보안과 접근성 위험을 검토했다.
- 남은 제한과 다음 행동이 기록된다.
- 검수 증거가 없으면 완료로 처리하지 않는다.

검수에서 실패하면 실패 원인에 따라 돌아갑니다. 환경 문제는 1단계, 문제 정의 오류는 2단계, 범위·완료 기준 오류는 3단계로 돌아가 수정한 뒤 다시 검수합니다.
